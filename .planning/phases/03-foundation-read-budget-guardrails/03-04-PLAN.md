## Flagged assumptions (edge probe — unresolved)

- **REND-06 — unclassified, unresolved.** The probe could not classify "a render manifest in KV
  records what has been rendered and at which version" into its shape taxonomy and returned
  "review manually". Reviewing it manually, the real unclassified edge is a *temporal* one the
  taxonomy has no category for: what the manifest claims and what is actually deployed can
  diverge, because a manifest write and an asset deploy are two operations with no shared
  transaction. **Residual assumption:** that a manifest entry written during a build whose
  deploy subsequently fails will be reconciled by the next build's content-hash comparison
  rather than leaving a permanently-lying entry. That reconciliation is Phase 4's incremental
  build (REND-02/REND-03), not this phase's, and it is not proven here. Recorded rather than
  dropped. Full 12-row ledger in `03-01-PLAN.md`.

    How is the Spanish counterpart identity populated in every manifest entry, from day one, so
    that Phase 6's hreflang pairing never forces a re-render of the corpus?
  </decision>
  <context>
    D-03 already locks the manifest key as one KV key per article, `manifest:<uuid>` — that is
    settled and is not what this asks. This is about the *field*, which D-04 rates **one-way**
    in its own words: "omitting it and adding it later is precisely the full-corpus re-render
    this field exists to prevent."

    There is a genuine contradiction sitting between two source documents, and it needs
    resolving before code sets it:

    - **ROADMAP Phase 3, success criterion 3** requires the manifest to *already carry* the
      Spanish counterpart ID per article, "so hreflang pairing never requires a backfill
      re-render of the corpus."
    - **03-RESEARCH.md's reference shape** declares the field `spanishCounterpartId: string |
      null` and annotates it "null until Phase 6 backfill."

    A field that is null for all 42,000 articles satisfies a test that checks the key exists,
    and satisfies a reading of "carries the field" — while delivering exactly none of the
    benefit the criterion describes. This plan's prohibition forbids that outcome, which is why
    the choice has to be explicit rather than inherited from a code sample.

    What undoing this costs: Phases 4 and 5 read the manifest, and Phase 6 pairs on this field
    across the full corpus. Changing the identity rule after those land means rewriting every
    manifest entry and updating every reader — and if the change is discovered *during* Phase 6,
    it means the corpus re-render this decision exists to avoid.

    One thing worth knowing before choosing: nothing in Phase 6's requirements (I18N-01 through
    I18N-10) yet says whether a Spanish summary will live as extra columns on the same D1 row or
    as a separate row with its own id. Option A assumes it needs an id of its own; Option C does
    not depend on the answer.
  </context>
  <options>
    <option id="option-a">
      <name>Derived counterpart id — compute it now from the English uuid</name>
      <pros>
        Never null, from the first entry written. Phase 6 needs no manifest backfill at all: the
        pairing is a pure function of the id it already has. Simplest possible reader.
      </pros>
      <cons>
        Commits Phase 6's Spanish-article identity scheme now, before Phase 6 has designed it. If
        Spanish summaries turn out to live as columns on the same D1 row rather than as rows with
        their own ids, every derived id points at a record that does not exist — a field that is
        confidently wrong rather than honestly empty.
      </cons>
    </option>
    <option id="option-b">
      <name>Nullable field, populated by a Phase 6 manifest rewrite</name>
      <pros>
        Commits to nothing about Phase 6's data model. A manifest rewrite is 42,000 KV bulk
        writes across ~5 calls, not a re-render of 42,000 pages, so the expensive thing the
        criterion names is still avoided.
      </pros>
      <cons>
        This is the outcome this plan's prohibition names. The field is structurally always null
        for the whole Phase 3-6 window, so nothing exercises it and any bug in its shape surfaces
        only in Phase 6. It satisfies the criterion's wording and not its intent, and the
        difference will not be visible in any test that checks key presence.
      </cons>
    </option>
    <option id="option-c">
      <name>Translation-group id plus a language field</name>
      <pros>
        Both language variants carry the same group id — set to the English article's uuid, so it
        is computable today with no new identity scheme invented. Pairing is a group lookup, which
        works identically whether Spanish ends up as a column on the same row or a separate row.
        Never null, and never wrong about a record that does not exist.
      </pros>
      <cons>
        Two fields instead of one, and readers must understand grouping rather than following a
        direct pointer. Slightly more to document, and the group id is redundant with the article
        id for every English-only article until Phase 6 arrives.
      </cons>
    </option>
  </options>
