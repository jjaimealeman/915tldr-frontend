|---|---|---|---|

| `acquisition_status` | TEXT, default `feed_fallback` | How each article's text was acquired: `fetched` / `feed_fallback` / `failed` | D-02 |

  <context>
**Why this is a one-way door.** D-06 already rates itself one-way: adding the column is a D1
migration, and once the v2 renderer reads `key_points` as an array rather than parsing
asterisks out of `summary` prose, reverting means both a schema change and a template change on
a published contract. Phase 1 built and the owner approved `summary-markdown.mjs`, the parser
for the legacy inline `**Key Details:**` shape; that parser stays live for un-re-processed rows
either way, but the moment new rows stop carrying the inline form, two shapes coexist in the
corpus permanently.

**The undo cost:** rolling back means a second production migration dropping four columns from
a 435 MB table, plus reverting whatever rows were written in the new shape back into the
concatenated-prose shape. There is no in-place undo.

**What is NOT being decided here:** whether to change any existing column. Nothing is dropped,
renamed or retyped, and no pre-existing row's `summary` value is rewritten by this migration.
