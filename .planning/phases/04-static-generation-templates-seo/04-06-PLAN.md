<planner_findings>
**RESEARCH's `not_found_handling: "404-page"` alone would silently break D-08 for real browsers.**
Cloudflare's docs (static-site-generation "Navigation requests", and the compatibility flag
"Navigation requests prefer asset serving", default since 2025-04-01 — this project's date is
2026-09-16): with a Worker `main`, a configured `not_found_handling`, and that date, a request
carrying `Sec-Fetch-Mode: navigate` does **not** invoke the Worker on an asset miss; the 404 page
is served instead. Browsers send that header on every link click; curl does not. A curl-based
check would pass while every reader clicking an old link got a 404. Fix: keep
`not_found_handling: "404-page"` (so `env.ASSETS.fetch` serves the styled 404 with status 404)
AND add the documented opt-out flag `assets_navigation_has_no_effect`, then verify with both
request kinds. Verified via Context7 `/llmstxt/developers_cloudflare_workers_llms-full_txt`
on 2026-09-26.

**D-09 check (short ids):** v1's `app/pages/[category]/[slug].vue` accepts an 8-character short
id, but no v1 link generator emits one (grep of 915tldr.com2 app/ and server/ for slice(0, 8),
substring(0, 8), shortId: no hits). Dropped as decided.

**D-11 check:** `/sources` is advertised in v1's sitemap (`server/routes/sitemap.xml.ts` static
list); `/categories` is linked from v1's `index.vue` and `about.vue`. Neither has a v2
equivalent page, so both redirect to `/`, whose nav lists every category (D-11 "homepage/nav").
</planner_findings>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Internet → Worker (asset misses only) | Fully untrusted request path and query |
| Worker → KV `RENDER_MANIFEST` | Build-written data read on the public path |
| Requested URL → 404 page script | Untrusted path tokens rendered next to titles |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-04-22 | Spoofing / Tampering | Worker 301 Location (open redirect) | high | mitigate | Location is built only by `articlePath` from validated manifest fields plus `url.search`; always a same-origin path starting with `/<category-slug>/` — it cannot begin with `//` or carry a host |
| T-04-23 | Tampering | Worker uuid parsing | medium | mitigate | Strict 36-char hex match on the decoded last segment, lowercased for the KV key; malformed encodings caught → 404 page |
| T-04-24 | Denial of Service | Worker CPU / KV on garbage URLs | medium | mitigate | No uuid → zero KV reads; at most one KV read per request; no loops; 404 served by the asset layer |
| T-04-25 | Tampering | 404 suggestion rendering (XSS) | high | mitigate | Suggestions rendered with createElement/setAttribute/textContent only; hrefs come from the build-time index, never from the requested path; test asserts no HTML-string sinks |
| T-04-26 | Elevation of Privilege | Worker reaching credentialed modules | high | mitigate | `src/worker.ts` added to the D1-import guard's exact entrypoints; fixture proves a transitive reach is rejected; wrangler.jsonc still declares no D1 binding |
| T-04-27 | Information Disclosure | Worker logs | low | mitigate | KV errors logged without request headers or cookies |
</threat_model>
