<planner_findings>
**The approved rail conflicts with criterion 3.** design/mockups/article.html ends every article
with "More in <Category>" (3 stories) and "Latest" (5 stories). Rendered into static HTML, a
site-wide "Latest" list changes on every build, so all ~40,000 article pages would differ on every
cron cycle: criterion 3 ("unchanged articles are byte-identical") fails, REND-05 becomes
unreachable, and every build re-uploads every article. The same holds for the footer build stamp
(OPS-05) — 04-02 added `stamp="commit"` for exactly this reason, and this plan switches article
pages to it. Owner decides the rail in Task 1.
</planner_findings>
</context>

  <name>Task 1: Decide how the article rail stays compatible with byte-identical unchanged articles</name>
  <decision>What the article rail shows, given that criterion 3 requires unchanged articles to re-render byte-identically</decision>
  <context>The approved mockup's rail ("More in &lt;Category&gt;" + "Latest") shows the newest stories at build time. Baked into ~40,000 static pages, it changes every article page on every 2-hourly build, defeating criterion 3 and REND-05 and forcing a full re-upload each cycle. The rail's layout and card markup are unaffected by this choice — only which stories fill it and one heading.</context>
  <options>
    <option id="option-a">
      <name>Article-relative rail (recommended)</name>
      <pros>"More in &lt;Category&gt;" = the 3 public stories in the same category published immediately before this one; second group = the 5 stories published immediately before this one site-wide, heading "Earlier". Pure static HTML, no JS, byte-identical until a neighbour is removed or retitled (then only the affected pages change, which is a real content change).</pros>
      <cons>The heading changes from the approved "Latest" to "Earlier"; a reader on an old story sees old neighbours, not today's news (the masthead nav and homepage still lead to today's news).</cons>
    </option>
    <option id="option-b">
      <name>Keep "Latest" baked into every page</name>
      <pros>Exactly the approved mockup.</pros>
      <cons>Every article page changes every build: criterion 3 fails, REND-05 cannot be met, all ~40,000 pages re-render and re-upload twelve times a day.</cons>
    </option>
    <option id="option-c">
      <name>Option A in HTML, true "Latest" swapped in by a plain page script</name>
      <pros>Static HTML stays byte-identical (option A is the no-JS state); readers with JS see today's 5 latest from a build-time /latest.json (zero D1, served as a static asset).</pros>
      <cons>Adds client JS and one extra request to every article view; risks layout shift in the rail on desktop; a script on every article page stretches ISL-08's five-island limit in spirit.</cons>
    </option>
  </options>
  <resume-signal>Select: option-a, option-b, or option-c</resume-signal>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| D1 summary/title text → HTML body via set:html | AI-generated from scraped RSS; the one place this plan uses set:html |
| D1 `url` → outbound link href | Original article URL from the outlet's feed |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-04-14 | Tampering | summaryBodyHtml → set:html | high | mitigate | Body HTML is produced only by design/scripts/lib/summary-markdown.mjs's closed block contract with render-time escaping, gated by validateBlocks; summary.test.mjs covers `<` and `&` in text |
| T-04-15 | Tampering | Outbound `href={article.url}` | medium | mitigate | The loader schema (04-01) restricts `url` to the http/https protocols, so a `javascript:` value fails the build; article-markup.test.mjs checks every sampled href starts with `https://` or `http://` |
| T-04-16 | Tampering | JSON-LD headline/description | high | mitigate | Serialised only through toSafeJsonLd (04-02) |
| T-04-17 | Spoofing | Misattributed reporting | medium | mitigate | Disclosure, attribution, byline and isBasedOn all read the same source row; the markup test asserts they agree |
</threat_model>
