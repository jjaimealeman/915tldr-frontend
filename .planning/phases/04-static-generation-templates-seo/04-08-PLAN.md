<planner_findings>
**How the build obtains v1's changelog.json (D-13 left this to research; research did not decide —
planner decision, reversible):** fetch it at build time from the live v1 URL
`https://915tldr.com/changelog.json`, overridable with `V1_CHANGELOG_URL`. Vendoring a copy would
go stale the moment the commit skill in 915tldr.com2 writes a new entry. The fail-loud rules make
the one real risk loud rather than silent: at cutover (Phase 12) 915tldr.com starts serving v2, so
this URL must be repointed then — a build against a URL that no longer serves the file fails and
notifies (D-15) instead of shipping an empty page. Phase 12 dependency recorded in the SUMMARY.

Measured 2026-09-26 (CONTEXT scout): 12 JSON entries (newest 2026-09-21) + 6 public D1 rows
(Dec 2025) = 18. Used as `CHANGELOG_MIN_EXPECTED` only when no last-good changelog count exists yet
(04-03 recorded an articles-only baseline).

`fetch()` in Node accepts `data:` URLs, so the regression test can point `V1_CHANGELOG_URL` at an
empty payload and run a real build with no test hooks in production code.
</planner_findings>
</context>
