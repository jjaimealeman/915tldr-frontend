<planner_findings>
**The incremental signal research proposed does not work as written.** D-06 suggests
`updated_at > last_sync`. Checked in 915tldr.com2 on 2026-09-26: the processing pipeline
(`server/utils/ai-processor.ts`) sets `processed_at`, not `updated_at`; duplicate flagging
(`server/utils/duplicate-detector.ts`) and tag linking set neither; only admin edits and
reprocess resets bump `updated_at`. `updated_at` also has no index, so any predicate on it scans
all ~43k rows — the same cost D-14 rejected for a per-build `COUNT(*)`. An article fetched as
`pending` and processed a cycle later would be missed forever.

**Design used instead (planner decision, reversible — loader internals only):**
- Warm path every build: re-read a rolling `published_at` window (3 days, indexed by
  `idx_articles_published_at`) — catches new articles, late processing, retitles and duplicate
  flags on recent rows. Cost scales with ~15 articles/cycle, not the corpus.
- Sweep once a day: `updated_at > ? OR processed_at > ?` (one unindexed scan, ~43k rows/day,
  ~2% of the 2M daily soft budget) — catches admin edits and very late processing.
- Cold resync every 7 days (and on empty cache or state-version change): the full bulk-fetch
  pass (~1M rows once), which also detects hard deletes and self-heals anything the two cheaper
  signals missed. Amortised ~140k rows/day.
- Projected total ≈ 240k rows/day (~12% of the soft budget); each mode is capped by a measured
  budget that fails the build when exceeded — the build-time rows-read guard the
  `d1-index-flip` incident showed Phase 3 lacked.

Staleness bound: any change the window and sweep miss (e.g. an admin re-linking a duplicate
older than 3 days, which bumps no timestamp) reaches the site within 7 days, or immediately with
`ARTICLES_FORCE_COLD=1`.
</planner_findings>
