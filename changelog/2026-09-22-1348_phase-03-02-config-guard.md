## Why

The D1-import assertion (`tools/assert-no-d1.mjs`, 03-01) walks Astro's resolved module graph —
but a Worker binding declared in `wrangler.jsonc` is config, not a module import, so it is
invisible to that walk by construction. 03-RESEARCH.md's own threat register calls this out
explicitly (T-03-01): a future contributor adding a `d1_databases` binding "just to try
something" would sail past the graph-walk guard entirely. This task closes that one remaining
gap with a cheap, deterministic, comment-aware string scan — plus the two removed-API guards
(ARCH-04, ARCH-05) that keep this repo from silently drifting back onto APIs that no longer exist
in the installed Astro/adapter versions.

## Issues Encountered

`@astrojs/cloudflare` v14.3.2's `cloudflare(options)` closes over the `imageService` option
inside its own function scope and never re-exposes it on the integration object it returns
(confirmed by reading `node_modules/@astrojs/cloudflare/dist/index.js` directly) — so
03-02-PLAN.md's literal instruction to "import astro.config.mjs and inspect the resolved exported
configuration object" for ARCH-06 doesn't work: there is no `config.adapter.imageService`
property to read. Worked around by evaluating (via `node:vm`, not a string match) the literal
object argument text passed to the `cloudflare(...)` call — this reads the real resolved value,
not source text positions, while sidestepping the adapter package's internal-closure limitation.
Recorded in full in `03-02-SUMMARY.md`.

Separately, the new guard's first real run against the repo failed — not because of a real
violation, but because of the stray `planner-discipline-allow` marker described above. Fixed by
removing the leaked line from `wrangler.jsonc`.
